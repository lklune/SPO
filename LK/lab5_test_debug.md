# Разбор тестов для lab 5


---------------------- types_basic.src ---------------------

Код:
type Base begin
    int a;
end

type Child of Base begin
    int b;
end

def main()
    Child c;
    int x;

    c.a = 10;
    c.b = 20;
    x = c.a + c.b;
end


Что тут проверяется:

-- объявление пользовательского типа
-- наследование Child of Base
-- доступ к унаследованному полю a
-- доступ к своему полю b
-- чтение и запись полей

Как это раскладывается:
-- `Base` содержит одно поле `a`
-- `a` имеет тип `int`, значит занимает `4` байта
-- размер `Base = 4`

Потом:
-- `Child` наследует `Base`
-- значит в начале объекта `Child` уже лежит всё содержимое `Base`
-- поле `a` остаётся на смещении `0`
-- новое поле `b` кладётся после `Base`, то есть на смещении `4`
-- размер `Child = 8`

Если переменная `c` начинается с адреса `0`, то:
-- `c.a` находится по адресу `0 + 0 = 0`
-- `c.b` находится по адресу `0 + 4 = 4`

Потом объявляется:
-- `int x`
-- `x` занимает ещё `4` байта
-- после объекта `c` размером `8` он попадает на адрес `8`

Лог:
asm
MOV 10, r0
ST r0, 0
MOV 20, r0
ST r0, 4
LD 0, r0
MOV r0, r1
LD 4, r0
ADD r1, r0
MOV r1, r0
ST r0, 8

Разбор:
-- `MOV 10, r0` загружается число `10`
-- `ST r0, 0` записывается в адрес `0`, это `c.a = 10`
-- `MOV 20, r0` загружается число `20`
-- `ST r0, 4` записывается в адрес `4`, это `c.b = 20`
-- `LD 0, r0` читается `c.a`
-- `MOV r0, r1` значение временно копируется в `r1`
-- `LD 4, r0` читается `c.b`
-- `ADD r1, r0` считается сумма
-- `ST r0, 8` результат пишется в `x`

То есть этот тест доказывает, что:
-- наследование работает
-- поля лежат по правильным адресам
-- кодогенерация умеет и писать в поле, и читать из поля




---------------------- types_nested.src ----------------------

Код:
type Point begin
    int x;
    int y;
end

type Line begin
    Point start;
    Point finish;
end

def main()
    Line l;
    int r;

    l.start.x = 7;
    l.finish.y = 9;
    r = l.start.x;
end

Что тут проверяется:
-- поле может быть не только `int`, но и другим пользовательским типом
-- доступ по цепочке `l.start.x`
-- доступ по цепочке `l.finish.y`
-- правильный размер вложенных объектов

Сначала:

-- `Point` содержит `x` и `y`
-- `x` на смещении `0`
-- `y` на смещении `4`
-- размер `Point = 8`

Дальше:
-- `Line` содержит `start` типа `Point`
-- потом `finish` типа `Point`

Значит:
-- `start` занимает `8` байт и начинается с `0`
-- `finish` кладётся после `start`, то есть на смещении `8`
-- размер `Line = 16`

Если переменная `l` начинается с адреса `0`, то:

-- `l.start.x` = `0 + 0 + 0 = 0`
-- `l.start.y` = `0 + 0 + 4 = 4`
-- `l.finish.x` = `0 + 8 + 0 = 8`
-- `l.finish.y` = `0 + 8 + 4 = 12`

Потом:
-- `int r` идёт после `l`
-- `l` занимает `16` байт
-- значит `r` попадает на адрес `16`

Лог:
asm
; .type Line size=16
; .field Line.start : Point offset=0 owner=Line
; .field Line.finish : Point offset=8 owner=Line
; .type Point size=8
; .field Point.x : int offset=0 owner=Point
; .field Point.y : int offset=4 owner=Point


Это как раз и показывает:
-- `Point` реально занимает `8`
-- `finish` лежит не на `4`, а на `8`


Почему линейный код такой:
asm
MOV 7, r0
ST r0, 0
MOV 9, r0
ST r0, 12
LD 0, r0
ST r0, 16

Разбор:
-- `ST r0, 0` это `l.start.x = 7`
-- `ST r0, 12` это `l.finish.y = 9`
-- `LD 0, r0` это чтение `l.start.x`
-- `ST r0, 16` это `r = l.start.x`


---------------------- types_method.src ----------------------

Код:
type Counter begin
    int value;

    def ping() of int
        int r;
        r = 123;
    end
end

def main()
    Counter c;
    int x;

    x = c.ping();
end


Проверяется:
-- внутри типа можно объявить метод
-- метод попадает в таблицу типов
-- метод становится отдельной функцией в коде
-- вызов через точку `c.ping()` превращается в обычный `CALL`

При генерации кода метод переименовывается в:
-- `Counter__ping`

Это сделано потому что:
-- чтобы не столкнулись методы с одинаковыми именами у разных типов
-- например `A.ping` и `B.ping`

То есть внутри asm уже нет "объектного" вызова, есть обычная функция:
asm
Counter__ping:
Counter__ping_L0:
MOV 123, r0
ST r0, 0
JMP Counter__ping_L1
Counter__ping_L1:
LD 0, r0
RET

Разбор:
-- внутри метода создаётся локальная `r`
-- она кладётся в память по адресу `0` внутри своей функции
-- `123` записывается в неё
-- потом `r` читается в `r0`
-- `RET` возвращает это значение

В main:
main:
main_L0:
CALL Counter__ping
ST r0, 4

Разбор:
-- вызывается метод `Counter__ping`
-- результат приходит в `r0`
-- потом пишется в `x`
-- почему адрес `4`
  потому что:
  -- `c` как `Counter` занимает `4` байта
  -- `x` идёт сразу после него
  -- значит `x` на адресе `4`







## 4. Что реально делает компилятор на этих тестах

Очень упрощённо цепочка такая:

1. парсер читает `type`, поля, методы, `a.b`, `obj.method()`
2. из этого строится AST
3. из AST собирается таблица типов
4. для каждого типа считаются:
   - размер
   - поля
   - offsets
   - связь с базовым типом
5. потом строятся CFG функций и методов
6. потом codegen:
   - выделяет память под переменные
   - если переменная имеет user type, выделяет не 4 байта, а весь размер объекта
   - если встречает `a.b.c`, считает адрес через цепочку offsets
   - если встречает `obj.method()`, ищет полное имя метода и делает `CALL`




----------------------- Идея по полям --------------------
Допустим есть:
l.finish.y

Компилятор считает это как адрес:
-- взять адрес `l`
-- прибавить offset поля `finish` в `Line`
-- прибавить offset поля `y` в `Point`

То есть:
-- `l` = `0`
-- `finish` = `8`
-- `y` = `4`

Итог:
-- `0 + 8 + 4 = 12`

Поэтому в asm и появился:
```asm
ST r0, 12
```

----------------------- Идея по методам -----------------------

Допустим есть:
c.ping()

Компилятор делает так:
-- определяет тип `c`, это `Counter`
-- ищет у `Counter` метод `ping`
-- находит его полное имя `Counter__ping`
-- генерирует:

```asm
CALL Counter__ping
```

То есть "вызов метода" у вас сейчас реализован как обычный вызов функции с заранее развёрнутым именем
