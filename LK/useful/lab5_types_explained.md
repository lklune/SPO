Главные структуры лежат тут:
-- [include/cfg.h](/C:/Users/december/Desktop/5_SPO/160526/SPO/LK/include/cfg.h)
-- [include/codegen.h](/C:/Users/december/Desktop/5_SPO/160526/SPO/LK/include/codegen.h)

Главная идея такая:

-- после 5 лабораторной этого уже мало
-- теперь нужно хранить сами пользовательские типы
-- нужно хранить их поля

-- нужно хранить связь с базовым типом
-- нужно хранить интерфейсы
-- нужно понимать размер объекта в памяти
-- нужно понимать, где именно лежит каждое поле


---------------------- Какие типы появились ----------------------

Добавлены такие структуры:
-- `UserTypeField`
-- `TypeNameNode`
-- `UserTypeMethod`
-- `UserType`
-- `TypeCollection`

И ещё расширены старые структуры:
-- `Function`
-- `AnalysisResult`
-- `VariableBinding`


---------------------- UserTypeField ----------------------

Эта структура хранит одно поле пользовательского типа

То есть если есть:
```txt
type Point begin
    int x;
    int y;
end
```

то у `Point` будет два `UserTypeField`
-- поле `x`
-- поле `y`

Что в нём хранится:
-- имя поля
-- тип поля
-- смещение поля в памяти
-- имя типа, в котором это поле было объявлено

Зачем это нужно:
-- чтобы знать, как обращаться к полю
-- чтобы правильно считать адрес
-- чтобы различать своё поле и унаследованное

Например:
-- `Point.x` может иметь `offset = 0`
-- `Point.y` может иметь `offset = 4`


---------------------- TypeNameNode ----------------------

Это маленькая служебная структура для списка имён типов

Сейчас она нужна в первую очередь для интерфейсов

Например если есть:
```txt
type Child implements ICounter, IPrintable begin
end
```

то у `Child` должен где-то храниться список:
-- `ICounter`
-- `IPrintable`

Вот для этого и нужен `TypeNameNode`

Он просто хранит:
-- имя одного типа
-- ссылку на следующий элемент списка


---------------------- UserTypeMethod ----------------------

Эта структура хранит один метод пользовательского типа

Например:
```txt
type Counter begin
    def ping() of int
        return 1;
    end
end
```

Для такого метода хранится:
-- короткое имя метода, например `ping`
-- полное имя метода для кода, например `Counter__ping`
-- полная сигнатура метода
-- возвращаемый тип
-- имя типа-владельца
-- AST-узел метода
-- признак, является ли метод абстрактным интерфейсным

Зачем это нужно:
-- короткое имя нужно для поиска по имени
-- полное имя нужно для генерации `CALL`
-- сигнатура нужна для проверки override
-- AST нужен, чтобы потом построить CFG и код

Полная сигнатура особенно важна для 5 лабораторной

Например:
-- `ping() of int`
-- `ping() of bool`

Это уже не одно и то же

Именно поэтому теперь хранится не только имя, но и полная сигнатура метода


---------------------- UserType ----------------------

Это главная структура пользовательского типа

Она описывает тип целиком

Например для:
```txt
type Child of Base implements ICounter begin
    int a;
end
```

в `UserType` хранится:
-- имя `Child`
-- базовый тип `Base`
-- список интерфейсов
-- список полей
-- список методов
-- размер типа в памяти
-- флаг, что это интерфейс или обычный тип

Зачем это нужно:
-- без этого нельзя собрать полное описание типа
-- нельзя посчитать размер объекта
-- нельзя проверить наследование
-- нельзя проверить `implements`

Тут же есть служебные флаги:
-- что тип уже посчитан
-- что тип сейчас находится в процессе расчёта

Они нужны, чтобы не попасть в циклы вроде:
-- `A` зависит от `B`
-- `B` зависит от `A`


---------------------- TypeCollection ----------------------

Это общая таблица всех пользовательских типов программы

Проще говоря:
-- все `type`
-- все `interface`

собираются в одну общую коллекцию

Зачем это нужно:
-- чтобы потом можно было найти тип по имени
-- чтобы из `Child` быстро дойти до `Base`
-- чтобы найти поле у типа
-- чтобы найти метод у типа
-- чтобы проверить интерфейс

Если бы этой таблицы не было, компилятору пришлось бы каждый раз снова обходить весь AST


---------------------- Function ----------------------

Эта структура была раньше, но для 5 лабораторной её пришлось расширить

Теперь в ней есть:
-- имя типа-владельца метода
-- признак, что это метод, а не обычная функция
-- ссылка на общую таблицу типов

Зачем это нужно:
-- чтобы codegen понимал, где обычная функция, а где метод
-- чтобы при генерации метода можно было знать его тип
-- чтобы во время codegen можно было искать поля и методы через таблицу типов


---------------------- AnalysisResult ----------------------

Это общий результат анализа программы

Раньше там были в основном:
-- функции
-- ошибки

Теперь туда добавлена ещё и таблица типов

Зачем это нужно:
-- чтобы после этапа анализа информация о типах не потерялась
-- чтобы export и codegen могли пользоваться этой таблицей дальше


---------------------- VariableBinding ----------------------

Это структура уже не про язык напрямую, а про кодогенерацию

Она хранит привязку переменной к памяти

Для 5 лабораторной она стала заметно важнее, потому что теперь переменная может быть не только `int`, но и целым объектом

Например:
```txt
Child c;
```

Тут уже недостаточно просто сказать:
-- есть переменная `c`

Нужно ещё знать:
-- какой у неё тип
-- какой у неё размер
-- где она лежит в памяти
-- является ли это пользовательским типом

Зачем это нужно:
-- чтобы под объект выделялось не всегда `4` байта
-- чтобы можно было правильно разложить поля
-- чтобы для `l.start.x` дойти до точного адреса


---------------------- Почему этого набора достаточно ----------------------

Этого набора структур хватает, чтобы закрыть 5 лабораторную в текущей модели проекта

Потому что:
-- `UserTypeField` хранит поля
-- `UserTypeMethod` хранит методы
-- `TypeNameNode` хранит список интерфейсов
-- `UserType` хранит тип целиком
-- `TypeCollection` хранит все типы программы
-- расширенный `Function` даёт методам связь с типом
-- расширенный `AnalysisResult` даёт доступ к таблице типов на поздних этапах
-- расширенный `VariableBinding` даёт правильную раскладку по памяти


---------------------- Как это потом используется ----------------------

После парсера всё идёт примерно так:

1. из AST собираются все пользовательские типы
2. у каждого типа собираются поля и методы
3. если есть базовый тип, запоминается связь с ним
4. если есть `implements`, запоминаются интерфейсы
5. потом считаются размеры типов и смещения полей
6. потом проверяется override
7. потом проверяется, что тип действительно реализует интерфейс
8. потом уже codegen использует всё это для адресов полей и вызовов методов


---------------------- Простой пример ----------------------

Если есть:
```txt
interface ICounter begin
    def ping() of int;
end

type Base begin
    def ping() of int
        return 1;
    end
end

type Child of Base implements ICounter begin
    int a;
end
```

то внутри структур это примерно так:

-- `ICounter` хранится как `UserType` с флагом интерфейса
-- у `ICounter` в методах лежит `ping() of int`
-- `Base` хранится как обычный `UserType`
-- у `Base` в методах лежит реализация `ping`
-- `Child` хранит имя базового типа `Base`
-- `Child` хранит список интерфейсов, где есть `ICounter`
-- `Child` хранит поле `a`

Потом проверки делают следующее:
-- у `Child` ищется интерфейс `ICounter`
-- у интерфейса читается метод `ping() of int`
-- компилятор ищет такой метод у `Child`
-- если не находит в самом `Child`, поднимается к `Base`
-- находит там `ping() of int`
-- сигнатура совпадает
-- значит `implements` считается корректным


---------------------- Что важно помнить ----------------------

В этом проекте методы сейчас работают в статической модели

Это значит:
-- вызов метода не идёт через настоящую виртуальную таблицу
-- вместо этого компилятор заранее находит нужный метод
-- и превращает его в обычный вызов функции с полным именем

Например:
-- `c.ping()`

превращается в:
```asm
CALL Counter__ping
```

То есть структуры данных уже поддерживают интерфейсы и override как правила языка
Но сама VM-модель вызова остаётся статической
