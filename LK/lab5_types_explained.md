# Разбор добавленных типов для lab 5

## Что добавлено

Для поддержки пользовательских типов ключевые структуры добавлены в [include/cfg.h](/C:/Users/december/Desktop/5_SPO/160526/SPO/LK/include/cfg.h), а служебные поля для кодогенерации расширены в [include/codegen.h](/C:/Users/december/Desktop/5_SPO/160526/SPO/LK/include/codegen.h)

Добавлены такие типы данных:

- `UserTypeField` нужен для хранения одного поля пользовательского типа
- `UserTypeMethod` нужен для хранения одного метода пользовательского типа
- `UserType` нужен для хранения полного описания одного пользовательского типа
- `TypeCollection` нужен для хранения всех пользовательских типов программы
- в `Function` добавлены поля, чтобы функция понимала, является ли она методом и к какому типу относится
- в `AnalysisResult` добавлено поле `types`, чтобы таблица типов жила вместе с результатом анализа
- в `VariableBinding` добавлены поля про тип, размер и признак пользовательского типа, чтобы кодогенерация могла правильно выделять память под объекты и поля

Почему именно так:

- один тип нельзя хранить просто строкой, потому что у него есть поля, методы, базовый тип и размер
- одно поле нельзя хранить только именем, потому что нужен ещё его тип и смещение в памяти
- один метод нельзя хранить только именем, потому что нужен return type и полное имя для asm
- все типы нужно хранить в одной общей таблице, чтобы потом можно было искать `Child`, находить у него `Base`, искать поле `a`, считать размер объекта и так далее
- кодогенерации уже мало знать только имя переменной, ей нужно знать размер объекта и тип, иначе вложенные поля и наследование не разложить по памяти правильно

## Построчно по структурам

### `UserTypeField`

Файл: [include/cfg.h](/C:/Users/december/Desktop/5_SPO/160526/SPO/LK/include/cfg.h)

- строка `typedef struct UserTypeField UserTypeField;`
  Это предварительное объявление структуры, чтобы потом можно было ссылаться на неё по имени
- строка `struct UserTypeField {`
  Начало описания структуры поля
- строка `char* name;`
  Имя поля, например `a`, `start`, `finish`
- строка `char* type_name;`
  Имя типа этого поля, например `int`, `Point`, `Base`
- строка `int offset;`
  Смещение поля внутри объекта в байтах
- строка `char* owner_type_name;`
  Имя типа, в котором поле было объявлено
  Это полезно при наследовании, чтобы понимать, своё это поле или пришло от предка
- строка `UserTypeField* next;`
  Ссылка на следующее поле в списке
  То есть поля внутри типа хранятся как связный список
- строка `};`
  Конец структуры

### `UserTypeMethod`

Файл: [include/cfg.h](/C:/Users/december/Desktop/5_SPO/160526/SPO/LK/include/cfg.h)

- строка `typedef struct UserTypeMethod UserTypeMethod;`
  Предварительное объявление структуры метода
- строка `struct UserTypeMethod {`
  Начало описания структуры метода
- строка `char* name;`
  Короткое имя метода, например `ping`
- строка `char* full_name;`
  Полное имя метода для генерации кода, например `Counter__ping`
  Это нужно, чтобы методы из разных типов не конфликтовали по именам
- строка `char* return_type;`
  Тип возвращаемого значения метода
- строка `Node* ast_node;`
  Указатель на AST-узел этого метода
  Потом по нему строится CFG и линейный код
- строка `UserTypeMethod* next;`
  Следующий метод в списке методов типа
- строка `};`
  Конец структуры

### `UserType`

Файл: [include/cfg.h](/C:/Users/december/Desktop/5_SPO/160526/SPO/LK/include/cfg.h)

- строка `typedef struct UserType UserType;`
  Предварительное объявление структуры пользовательского типа
- строка `struct UserType {`
  Начало описания типа
- строка `char* name;`
  Имя типа, например `Base`, `Child`, `Point`
- строка `char* base_type_name;`
  Имя базового типа, если есть наследование
  Если наследования нет, тут будет `NULL`
- строка `UserTypeField* fields;`
  Список полей этого типа
- строка `UserTypeMethod* methods;`
  Список методов этого типа
- строка `int size_bytes;`
  Общий размер объекта этого типа в памяти
  Он считается после разбора всех полей и базового типа
- строка `int resolved;`
  Флаг, что размер и offsets уже посчитаны
- строка `int resolving;`
  Временный флаг во время расчёта
  Нужен, чтобы ловить циклы вроде `A -> B -> A`
- строка `UserType* next;`
  Следующий тип в общей таблице типов
- строка `};`
  Конец структуры

### `Function`

Файл: [include/cfg.h](/C:/Users/december/Desktop/5_SPO/160526/SPO/LK/include/cfg.h)

Здесь структура была расширена, а не создана с нуля

  Следующая функция в списке

### `VariableBinding`

Файл: [include/codegen.h](/C:/Users/december/Desktop/5_SPO/160526/SPO/LK/include/codegen.h)

Это уже не описание типа языка, а служебная структура кодогенератора, но для lab 5 она тоже стала важной

- строка `char* var_name;`
  Имя переменной или поля
- строка `char* type_name;`
  Имя типа этой переменной
  Раньше для обычных простых переменных это было не так важно, а для user type стало обязательно
- строка `int register_id;`
  Привязка к регистру, если используется
- строка `int memory_address;`
  Адрес в памяти
- строка `int size_bytes;`
  Размер в байтах
  Именно это поле позволяет выделять не 4 байта всегда, а реальный размер объекта
- строка `int is_argument;`
  Признак аргумента функции
- строка `int is_user_type;`
  Признак, что переменная имеет пользовательский тип
- строки `is_constant`, `constant_value`
  Старые служебные поля для констант

## Зачем этого набора достаточно

Этих структур хватает для всех нужд lab 5:

- `UserTypeField` решает задачу хранения полей
- `UserTypeMethod` решает задачу хранения методов
- `UserType` решает задачу хранения самого типа и его наследования
- `TypeCollection` решает задачу глобального поиска типов
- расширенный `Function` даёт методам связь с типом
- расширенный `AnalysisResult` даёт доступ к таблице типов на поздних этапах
- расширенный `VariableBinding` позволяет правильно выделять память под объекты и поля
